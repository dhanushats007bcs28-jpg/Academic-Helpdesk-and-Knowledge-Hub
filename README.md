# Academic Helpdesk and Knowledge Hub

## About the Project

Academic Helpdesk and Knowledge Hub is a web application designed to make academic support, knowledge sharing, and student project development easier within an educational institution.

Students often have doubts about subjects, assignments, academic procedures, and project development. Finding the right person to answer these questions can take time, while useful solutions and previous project experiences may not always be easy to access.

This project brings these activities together in one platform. Students can search for existing answers, raise support tickets, track their requests, find academic resources, and work on projects with faculty guidance. Faculty members can respond to queries and mentor students, HODs can monitor departmental activities, and administrators can manage the platform.

The project combines three important areas: academic helpdesk services, a knowledge-sharing platform, and a structured project development system through Project Pulse.

## Problem Statement

In many educational institutions, academic queries are handled through direct communication, emails, or informal messaging. This can make it difficult for students to track their requests and receive timely responses. Faculty members may also spend time answering similar questions repeatedly.

Project development presents another challenge. Students may find it difficult to obtain continuous mentorship, organize team activities, track weekly progress, and learn from projects completed by previous batches. Project knowledge can remain limited to individual teams instead of becoming a resource for the wider student community.

There is a need for a centralized platform that supports academic queries, organizes knowledge, improves project mentorship, and preserves useful project outcomes for future students.

## Objectives

The main objectives of this project are to:

- Provide a centralized platform for academic queries and support requests.
- Help students find existing answers before submitting new tickets.
- Organize academic resources in a searchable knowledge base.
- Improve communication between students, faculty members, and department heads.
- Support structured project mentorship and progress tracking.
- Encourage team collaboration during project development.
- Preserve completed project information for future batches.
- Monitor ticket timelines and escalate eligible overdue requests.
- Improve accountability and knowledge sharing within the institution.

## Key Features

### 1. Knowledge Hub

The Knowledge Hub provides a common place to search for existing answers and access useful academic resources.

Before raising a ticket, students can look for relevant articles that may help them resolve their doubts. This reduces unnecessary repetition and makes previously documented knowledge easier to find.

The knowledge base can also support long-term knowledge sharing by organizing useful information and project documentation.

### 2. Academic Helpdesk

The helpdesk allows students to submit academic queries as tickets by selecting relevant details such as department, semester, subject, and category.

Students can track their requests and view updates, while faculty members can review and respond to assigned tickets. The system provides a structured process for managing academic queries instead of relying entirely on informal communication.

### 3. Student Dashboard

The student dashboard provides access to the application's student-facing features.

Students can search knowledge resources, raise support tickets, view submitted requests, follow ticket progress, and access relevant project-related features available to them.

### 4. Faculty Dashboard

Faculty members can view assigned tickets, understand student concerns, respond to queries, and update ticket statuses.

The platform also supports the project mentorship workflow, allowing faculty members to guide students and review their project progress through Project Pulse where enabled.

### 5. HOD Dashboard

The HOD dashboard helps department heads monitor academic support activities and review unresolved or overdue tickets.

HODs can handle tickets escalated under the configured SLA rules and gain better visibility into departmental support requests.

### 6. Admin Dashboard

The administrator module provides facilities for managing users, academic information, knowledge resources, and other aspects of the platform.

It supports centralized administration of the system and helps maintain organized access for different user roles.

### 7. SLA Monitoring and Escalation

The system includes a Service Level Agreement (SLA) mechanism to monitor ticket timelines.

The configured defaults are:

- SLA target: 24 working hours.
- Working hours: 9:00 AM to 5:00 PM.
- Working days: Monday through Friday.
- SLA monitoring interval: Every 15 minutes.

Tickets that meet the configured overdue conditions can be escalated to the HOD. This helps departments identify requests that require additional attention and encourages timely handling of academic queries.

### 8. Notifications and Attachments

The application supports ticket-related updates and attachments where enabled. These features help students and faculty members exchange relevant information and follow changes in the support process.

Notifications can also support project-related communication, helping participants stay informed about updates and feedback where implemented.

## Project Pulse: Project Mentorship and Development

Project Pulse extends the platform beyond conventional academic ticket management. It provides a structured approach to student project development, with the goal of connecting students, teams, and faculty mentors throughout the project lifecycle.

Instead of limiting project guidance to occasional meetings or final evaluations, the module aims to support continuous engagement, organized progress tracking, and knowledge sharing.

### 1. Project Mentorship

Students can request faculty mentorship for their projects. The mentorship workflow helps organize requests and their approval or rejection, providing a clearer process for connecting students with guidance.

### 2. Team Formation and Collaboration

Project Pulse supports team formation as part of project development. Students can work together around a shared project and coordinate their activities through the available project-related features.

This encourages teamwork and helps make responsibilities and progress easier to follow.

### 3. Weekly Progress Tracking

Students can submit weekly tasks and progress updates, including supporting attachments where available.

Mentors can review submissions, provide feedback, suggest corrections, and guide students on their next steps. Regular progress updates help identify difficulties earlier rather than waiting until the end of the project.

### 4. Project Communication and Notifications

Project-related communication and notifications help students and mentors stay informed about relevant updates, submissions, and feedback where supported by the implementation.

This creates a more organized way to follow project activities and maintain communication during development.

### 5. Semester-End Project Gallery

The project gallery is intended to showcase completed or approved student projects across academic years.

Students can explore previous projects, understand the technologies used, and discover ideas for future work. Project details may include abstracts, outcomes, and repository or demonstration links where available.

This helps useful project experiences reach a wider student community instead of remaining limited to the original team.

### 6. Preserving Project Knowledge

A key idea behind Project Pulse is to make project outcomes useful beyond the semester in which they were created.

By connecting published projects and their documentation with the wider knowledge-sharing experience, the platform can help future batches explore earlier work and learn from previous implementations.

Over time, this can contribute to a growing collection of institutional project knowledge.

## Innovation and Uniqueness

The main innovation of Academic Helpdesk and Knowledge Hub is the integration of academic support, knowledge sharing, and project development within one platform.

A conventional helpdesk primarily focuses on receiving tickets and resolving individual issues. This project extends that approach by supporting students throughout a broader academic journey, from finding answers to developing projects and sharing their outcomes.

### 1. Beyond a Conventional Ticketing System

The platform does more than manage support requests. It combines the helpdesk with a searchable Knowledge Hub and the Project Pulse mentorship workflow.

Students can first look for an existing solution, request assistance when necessary, and access project-related guidance within the same application.

### 2. Continuous Project Mentorship

Project Pulse introduces a structured approach to ongoing project guidance through mentorship requests, team activities, and progress submissions.

This helps connect students and mentors throughout project development rather than treating mentorship as an isolated activity.

### 3. Knowledge That Carries Forward

The project gallery and knowledge-sharing concept aim to preserve the outcomes of completed projects.

Students from later batches can explore previous work, understand the approaches used, and identify opportunities to develop new ideas. This encourages knowledge continuity across academic years.

### 4. Knowledge-First Query Resolution

The platform encourages students to search existing resources before raising a new ticket.

This approach can reduce repeated questions, make documented solutions more useful, and allow faculty members to focus on queries that require additional assistance.

### 5. Structured Accountability

Ticket tracking, SLA monitoring, and eligible overdue-ticket escalation provide a more transparent support process.

The project mentorship workflow complements this by introducing regular progress updates and feedback during project development.

### 6. One Platform for Multiple Academic Needs

The platform brings together three connected areas:

- **Academic support:** Raising queries, tracking tickets, and receiving assistance.
- **Project development:** Requesting mentorship, forming teams, and tracking progress.
- **Knowledge sharing:** Finding existing answers and exploring previous project outcomes.

The uniqueness lies in connecting these areas rather than treating them as unrelated activities.

## How the System Works

The general academic support workflow is:

1. A student opens the application and searches for an existing answer.
2. If a suitable knowledge resource is available, the student can use it to resolve the query.
3. If further assistance is required, the student submits a ticket with relevant academic details.
4. The ticket is processed through the application's assignment workflow.
5. The assigned faculty member reviews the query and updates its status.
6. The student follows the progress of the request.
7. The SLA monitoring process checks the ticket's timeline.
8. Eligible overdue tickets are escalated to the HOD.
9. The ticket proceeds through the resolution process.

The Project Pulse workflow complements this process:

1. A student requests mentorship for a project.
2. The request follows the configured approval process.
3. Students organize their project team where supported.
4. The team works on project tasks and submits progress updates.
5. The mentor reviews submissions and provides feedback.
6. Completed or approved projects can be showcased through the project gallery where implemented.
7. Published project information can help future students explore previous work.

## Getting Started

### Prerequisites

Install the following before running the project:

- Node.js and npm
- MongoDB locally or a MongoDB Atlas account
- Git

### 1. Clone the Repository

```bash
git clone https://github.com/dhanushats007bcs28-jpg/Academic-Helpdesk-and-Knowledge-Hub.git
cd Academic-Helpdesk-and-Knowledge-Hub/webapp
```

### 2. Configure the Backend

Navigate to the server directory and install the dependencies.

```bash
cd server
npm install
```

Create a `.env` file in the server directory with the environment variables required by the application.

Example configuration:

```env
PORT=3000
JWT_EXPIRES_IN=7d
WORKDAY_HOURS=8
WORKDAY_START=09:00
WORKDAY_END=17:00
SLA_HOURS=24
```

Configure the MongoDB connection URI and JWT secret using the exact variable names expected by the backend source code.

Do not commit database credentials, JWT secrets, or other sensitive configuration to GitHub.

Start the backend using the script defined in `server/package.json`. For example:

```bash
npm run dev
```

### 3. Configure the Frontend

Open another terminal and navigate to the client directory.

```bash
cd client
npm install
```

If the frontend uses the `VITE_API_URL` environment variable, configure it in the client's environment file.

For a local backend using the `/api` prefix, the value may look like this:

```env
VITE_API_URL=http://localhost:3000/api
```

Confirm the API prefix and configuration expected by your application before using this value.

Start the frontend:

```bash
npm run dev
```

Open the local URL shown in the terminal, usually `http://localhost:5173`.

If the root project already provides a script to start both frontend and backend services, that script can be used instead.

## Deployment

The project can be deployed using Render, with MongoDB Atlas as the database.

### Backend Deployment

1. Create a Render Web Service connected to the GitHub repository.
2. Set the root directory to `webapp/server`.
3. Install the required dependencies.
4. Configure the appropriate start command.
5. Add the required environment variables in Render.
6. Ensure the deployed backend can connect to MongoDB Atlas.

### Frontend Deployment

1. Create a Render Static Site connected to the same repository.
2. Set the root directory to `webapp/client`.
3. Set the build command to `npm install && npm run build`.
4. Set the publish directory to `dist`.
5. Configure `VITE_API_URL` to point to the deployed backend API.
6. Configure backend CORS settings to allow requests from the frontend's deployed origin.
